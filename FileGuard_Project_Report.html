Abstract

FileGuard is a browser-based file integrity verification tool built with Python and Streamlit. It computes the SHA-256 cryptographic hash of any uploaded file, allows the user to record that hash as a trusted reference, and compares a file’s current hash against the reference at any later time to determine whether the file has been changed.

The application runs entirely on the user’s local machine. No file content, hash, or metadata is transmitted to any external server. Files are never written to disk and are never executed.

The tool addresses a practical gap: existing hash verification utilities are either command-line tools unfamiliar to beginners or heavyweight enterprise systems. FileGuard provides the same underlying verification method — SHA-256 comparison — through a clean, step-by-step browser interface that requires no technical background to operate.

Key capabilities include SHA-256 hash computation, original reference recording, structured JSON export and import for cross-session verification, side-by-side hash comparison, colour-coded pass/fail verdicts, and a downloadable plain-text verification report.

1. Introduction

1.1 Background

Digital files are the primary medium through which information is created, shared, and stored. A document, a software installer, a database export, or a configuration file may pass through email servers, cloud storage platforms, USB drives, and network file shares before reaching its intended recipient. At every step, the file is vulnerable to unintended or malicious modification.

Traditional antivirus software detects known malware signatures, but it does not answer a simpler, equally important question: “Is this the exact file I originally had?” Cryptographic hash functions provide a mathematically precise answer to that question.

1.2 Motivation

A first-year engineering or cybersecurity student typically learns about SHA-256 from textbooks but has no accessible tool to interact with it hands-on without using a terminal command. FileGuard was developed to bridge that gap — to make a real security primitive usable by anyone with a browser.

2. Problem Statement

Files shared over networks, stored in cloud drives, or passed between systems are vulnerable to silent modification. Causes include:

  • Transmission errors during network transfer or storage media degradation.
  • Software bugs in editors, converters, or synchronisation tools.
  • Deliberate tampering by an attacker who has access to the file at any point in its journey.

Without an independent integrity check, there is no reliable way to confirm that the copy of a file you have today is byte-for-byte identical to the version that was originally created or distributed.

Existing tools fall into two categories:

  1. Command-line utilities (sha256sum on Linux/macOS, certutil -hashfile on Windows) — effective but inaccessible to users who are not comfortable with terminals.
  2. Enterprise FIM tools (Tripwire, AIDE, osquery) — powerful but complex, requiring installation, configuration, and system-level access.

There is no lightweight, beginner-friendly, browser-based tool that covers the complete workflow: compute a hash, save it as a reference, and verify a file against that reference in a later session.

3. Objectives

  1. Compute the SHA-256 hash of any uploaded file entirely within the user’s browser session, without transmitting file contents to any server.
  2. Allow the user to record a computed hash as a trusted original reference, with a UTC timestamp and the original filename.
  3. Export the recorded reference as a structured JSON file that can be stored securely and used in a future session.
  4. Import a previously exported JSON record and validate its structure and SHA-256 format before using it as a reference.
  5. Compare the current hash of a file against the active reference and display a clear, colour-coded pass/fail verdict.
  6. Show both hashes side-by-side in selectable text areas so the user can inspect them directly.
  7. Generate a downloadable plain-text verification report containing the filenames, both hashes, the verification timestamp, and the result.
  8. Explain the meaning and limitations of hash-based verification in plain language within the application itself.
  9. Enforce safety controls: size limits, no file execution, no permanent storage, and honest messaging about what a hash match does and does not guarantee.

4. Scope of the Project

In Scope

  • SHA-256 hash computation for any file up to 10 MB in size.

  • Multi-user or networked deployment.
  • Automated or scheduled integrity monitoring.
  • PDF report generation (identified as a future enhancement).
  • Verification of more than one file at a time in a single session.

5. Existing Approach and Proposed Solution

5.1 Existing Approach

The standard method for manual file integrity verification is to use a command-line tool:

# Linux / macOS
sha256sum report.pdf

# Windows
certutil -hashfile report.pdf SHA256

This approach requires the user to open a terminal, type a command with exact syntax, copy and save the output manually, re-run the command later, and compare two strings by eye. For a student or non-technical user, this workflow is a barrier.

5.2 Proposed Solution

FileGuard wraps the same underlying primitive — SHA-256 via Python’s hashlib — in a browser interface that guides the user through each step:

  1. Step 1: Upload a file, see the hash, click one button to record it.
  2. Export: Download the reference as a JSON file for safe keeping.
  3. Step 2: Upload the file again (or load the saved record), see both hashes side-by-side, and receive an immediate verdict.

All components run in a single Python process on the user’s machine. No database connections, no external API calls, no file system writes.

8.2 Data Flow — Recording a Reference Hash

  1. User selects a file via st.file_uploader in Step 1.
  2. Streamlit reads the file into memory as a bytes object.
  3. Size is checked: if it exceeds 10 MB or is zero, an error is shown and processing stops.
  4. compute_sha256() reads the bytes in 64 KB chunks and returns the 64-character hex digest.
  5. The hash is displayed in a st.text_area widget.
  6. Clicking “Record as original reference” saves the hash, filename, and UTC timestamp to st.session_state.
  7. The sidebar updates immediately to show the active reference.

8.3 Data Flow — JSON Export

  1. User expands the “Active reference hash” panel and clicks the download button.
  2. build_record() assembles a Python dictionary with schema version, tool name, filename, hash, and timestamp.
  3. json.dumps() serialises it; st.download_button offers it as a .json file download.

8.4 Data Flow — Verification

  1. User optionally uploads a saved .json record in Step 2 Option A (parsed with json.loads(), never executed).
  2. validate_record() checks required fields, the "tool" sentinel, and SHA-256 format.
  3. If no JSON record is uploaded, the session-state reference from Step 1 is used.
  4. User uploads the file to verify in Option B; compute_sha256() computes its current hash.
  5. The two hashes are compared with string equality (==).
  6. A colour-coded verdict banner is shown. Both hashes are displayed side-by-side.
  7. build_verification_report() assembles a plain-text report offered via st.download_button.

9. SHA-256 Hashing Explanation

9.1 What SHA-256 Is

SHA-256 (Secure Hash Algorithm, 256-bit output) is a member of the SHA-2 family standardised by NIST in FIPS PUB 180-4. It takes an input of arbitrary length and produces a fixed 256-bit (32-byte) output written as a 64-character lowercase hexadecimal string.

9.2 Key Properties

  • Deterministic. The same bytes always produce the same hash.
  • Avalanche effect. A single bit change produces a completely different hash.
  • Pre-image resistance. A hash cannot be reversed to recover the original file.
  • Collision resistance. It is computationally infeasible to find two different files with the same hash.

9.3 How FileGuard Uses SHA-256

def compute_sha256(file_bytes: bytes) -> str:
    h = hashlib.sha256()
    stream = io.BytesIO(file_bytes)
    while chunk := stream.read(65536):   # 64 KB chunks
        h.update(chunk)
    return h.hexdigest()

9.4 Example — Avalanche Effect

Input: "Hello, World!"
SHA-256: dffd6021bb2bd5b0af676290809ec3a53191dd81c7f70a4b28688a362182986f

Input: "Hello, World?"   (only last character changed)
SHA-256: f16c3bb0532537acd5b2e418f2b1235b29181e35cffee7cc29d84de4a1d62e4d

Every single character of the hash is different despite only one character changing in the input — this is the avalanche effect.

9.5 What a Hash Match and Mismatch Each Mean

Match: Every byte of the file is identical to the original reference. The file has not been altered, corrupted, or substituted.

Mismatch: The file’s byte content differs. Possible causes: intentional edit, accidental corruption, wrong version uploaded, or malicious tampering. A mismatch does not by itself identify the cause.

Important: A hash match confirms identity only — not that the file is free of malware. FileGuard is not an antivirus tool.

14. Advantages

  1. No installation complexity. Once Python and Streamlit are installed, the app starts with a single command.
  2. No external dependencies beyond Streamlit. All cryptographic logic uses Python’s standard library.
  3. Completely local. No data ever leaves the user’s machine — suitable for sensitive documents.
  4. Files are never executed. The application reads only raw bytes.
  5. Cross-session verification. The JSON export/import mechanism allows a hash recorded today to verify the same file weeks later.
  6. Honest about limitations. Explicitly states what SHA-256 verification does and does not prove.
  7. Educational value. The SHA-256 explainer and character-level diff teach hashing through direct interaction.
  8. Accessible to beginners. The entire workflow is two numbered steps; no terminal knowledge required.

15. Limitations

  1. Single file per session. Only one reference hash can be recorded per session.
  2. Session volatility. Reference hash is lost on browser tab refresh if the JSON record was not exported.
  3. No pytest integration or CI pipeline. The built-in self-test suite must be run manually with python app.py.
  4. 10 MB file size limit. Large files cannot be verified.
  5. SHA-256 only. MD5, SHA-1, and SHA-512 are not supported.
  6. No digital signature on the JSON record. If an attacker modifies both the file and the record, the comparison provides no guarantee.
  7. No verification history. Each comparison session starts fresh.
  8. Browser dependency. The application cannot run as a background service.

17. Conclusion

FileGuard demonstrates a practical application of cryptographic hashing to the real-world problem of file integrity verification. By wrapping Python’s hashlib.sha256() in a Streamlit interface, the project makes a professional-grade security technique accessible to users with no terminal or cryptography background.

The application covers the complete verification workflow: hash a file, record the reference, export it for safe keeping, reload it in a future session, compare the current hash of the file, interpret the result, and download a report.

The codebase is intentionally minimal — four files, one external dependency — making it straightforward to understand, extend, and audit. The safety controls reflect sound principles: no file execution, no data transmission, enforced input limits, structured validation of imported data, and careful honesty about what the tool can and cannot guarantee.

This project demonstrates competence in Python programming, web application development with Streamlit, cryptographic concepts, input validation, session management, structured data exchange with JSON, and security-aware software design.
